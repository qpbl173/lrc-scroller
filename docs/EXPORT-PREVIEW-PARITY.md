# 导出 = 预览：一致性修复报告

> 起因：用户发现「导出功能导出的视频文件」与「网页预览」动效不同。
> 经实测定位，差异不止动效一处，根因是**导出用 canvas 另写了一套排版与动画**，
> 与预览的 DOM + CSS 各自演化，越改越远。

## 一、实测到的差异（全部有数据支撑）

| # | 项目 | 预览（DOM + CSS） | 导出（修复前 canvas） |
|---|---|---|---|
| 1 | 行切换的缩放过渡 | `transform 260ms cubic-bezier(.22,1,.36,1)` | **同帧瞬跳**到 1.35 |
| 2 | 行切换的颜色/透明度过渡 | `color/opacity 180ms ease` | 同帧瞬变 |
| 3 | 滚动平滑 | rAF 每帧先平滑再写 transform | 存的是更新前的值 → **稳定滞后一帧** |
| 4 | 行高 | 逐行实测 `offsetTop/offsetHeight` | 全行等高的单一 `lineH` |
| 5 | 间奏空行 | 显示「（间奏）」 | `continue` 跳过 → **整行空白** |
| 6 | 双语翻译行 | `font-size: 0.62em` | 与正文同尺寸 |
| 7 | `scrollMode: golden` | 当前行停在 38% | 恒定 50% |
| 8 | `reduceMotion` | 不做缩放、滚动直接对齐 | 照旧放大 + 缓动 |
| 9 | 左/右对齐 | 文字块贴边 | 内缩 5% |
| 10 | 首行之前（`activeIndex=-1`） | 没有任何行是 active | 强制把第 0 行放大变色 |
| 11 | 换行位置 | 按舞台宽度算 | 按画布宽度算（宽高比不同就不同） |

其中 **#4 是最隐蔽也最严重的一条**：预览按行实测几何，导出假设所有行等高。
只要有一行自动换行（长句、调大字号、调小 `maxWidth` 都会触发），
**后面每一行都会越偏越多**。实测单个换行行使后续行偏移 64px：

```
row  文本                预览实测高   预览居中位移   导出居中位移   偏差
0    短句A                  78.4        -76.80        -76.80      0.00
1    这一句特别长…（换行）    142.4         33.60          1.60    -32.00
2    短句B                   78.4        144.00         80.00    -64.00
3    短句C                   78.4        222.40        158.40    -64.00
```

## 二、修复思路

核心原则：**预览是唯一事实来源，导出不再自己算一套。**

导出开始时从预览 DOM 实测几何（舞台宽高、逐行高度、上下留白），
换算到画布像素；动效全部由纯函数逐帧重放 CSS 的曲线与时长。

这样"任何自定义"都自动跟随，而不是逐个设置去补分支。

## 七、调色盘：指向大红色却输出淡红色

### 根因（两个叠加的 bug，都靠像素比对才抓出来）

**1. 色轮遮罩方向是反的**

`pointToHS` 是"半径越大饱和度越高"（圆心 S=0 → 圆边 S=100），
但 `wheelGradient` 的径向遮罩写的是"圆心透明（满饱和）→ 边缘盖灰"，
两者正好相反。于是：

```
半径     色轮显示    点下去得到
0.15     S=100%      S=15%    ← 指向大红，得到淡粉 #ffd5d9
0.55     S=55%       S=55%    ← 只有这里偶然相等
1.00     S=12%       S=100%   ← 完全反过来
```

**2. `radial-gradient` 默认尺寸是 `farthest-corner`**

`radial-gradient(circle at center, …)` 的默认尺寸不是"半边长"，
而是**半对角线**：120×120 的圆里是 84.85px 而非 60px。
百分比停靠点被整体拉伸 1.41 倍，边缘本该 S=100 却只画到 S≈68，整轮发白。

### 修法

让绘制与取色**共用同一个函数**，从结构上消除再次错位的可能：

- 新增 `wheelSaturationAt(radiusRatio)`，`pointToHS` 与 `wheelGradient` 都调它；
- 遮罩不透明度由饱和度**反解**而来（`a = 1 - S/100`），不再手调百分比；
- 显式写 `circle closest-side`，并让取色半径与它同为"半边长"（去掉原来的 `-2` 内缩）；
- 死区边界补两个停靠点，否则浏览器会把那条硬边平滑掉。

### 验证（读真实渲染像素）

```
 frac   渲染像素    像素 S%   点击 S%   一致
 0.30   #d8ffb5      29.0      30.0     yes
 0.50   #beff81      49.4      50.0     yes
 0.80   #9bff39      77.6      80.0     yes
 1.00   #81ff07      97.3     100.0     yes

最大偏差 2.7 个百分点（修复前 31.4）—— 残差来自 8bit 量化与渐变插值
```

## 八、移除「感知 / 线性」切换

按要求删掉插值模式选择，只保留线性，相关 UI 一并删除。

理由也是正确性：**「感知」会让把手位置与实际明度脱钩**
（位置过一层 smoothstep 逆变换），出现"把手在这、颜色在那"。
明度条是取值控件，位置必须严格等于取值。

清理范围：`INTERP_MODES` / `applyInterpolation` / ColorPicker 的
`interpMode`、`inverseSmoothstep`、`.cp__seg` 样式、5 个已失效的 import。
`valueGradient` 签名简化为 `(h, s, steps?)`。

**聚光灯用 `box-shadow: 0 0 0 9999px` 挖洞**，而不是拼四个遮罩块 ——

**教程进行中独占键盘**。这是必须的：教程用 ←/→/Enter/Esc 翻页，

`useKeyboard.onKeydown` 在**最前面**判断 `tut.active` 并直接返回；
遮罩自身在捕获阶段先处理并 `preventDefault`。
已实测：教程开着按 →/空格，播放头与播放状态纹丝不动；
关闭后 → 立刻恢复快进 5 秒（证明拦截确实生效）。

**目标滚进视野**。第 4 步的目标在可滚动的设置抽屉里，
实测 `rect.top ≈ 2181px` 而视口只有约 850px ——
不滚动的话聚光灯画在屏幕外，用户只看到"让我点导出，可我什么都看不到"。
现在换步或目标变化时会把它滚到可视区中部（实测修正为 745/484）。

**目标选择器用 `data-tour="…"`**，不用 class：
class 是样式用的、重构时容易被改掉；`data-tour` 只服务教程。

# 第四轮：竖版画布（9:16 / 3:4）

## 十二、把「比例」提升为一等设置

### 需求

导出本来只有 16:9。短视频要 9:16、小红书图文要 3:4，
而且**预览必须就是导出的样子** —— 不能「预览按窗口随便收缩、导出固定 16:9」。

### 关键决定：比例是渲染参数，不是导出参数

最容易走偏的做法是「导出时按比例裁切」。那等于两套版式：
预览里一行放得下，导出裁完就放不下。所以比例必须**同时**作用于预览舞台。

| 层 | 做法 |
|---|---|
| 数据 | `settings.export.aspect`（`16:9` / `9:16` / `3:4`） |
| 预览 | `.stage` 自己按比例收窄居中（`aspect-ratio`），留白由 `.stage-frame` 上底色 |
| 导出 | 画布尺寸 = `findResolution(resolution, aspect)`；几何仍读 `.stage` 的实测值 |
| 渲染 | 不变 —— `core/renderFrame` 只认 `referenceHeight` 算缩放系数 |

**为什么必须改 `.stage` 本身，而不是外面套一层窄容器**：
`core/stageGeometry` 量的是 `.stage`。若只让外壳变窄、`.stage` 继续铺满，
预览是竖版、导出却按宽屏算版心，换行与行高全部错位。
让 `.stage` 真的变成目标比例后，`k = 画布高 / 舞台高` 在横竖两个方向相同，
导出与预览才是同一套几何。

### 尺寸表：按「短边」命名

竖版的短边是宽，所以 1080p 在 9:16 下是 **1080×1920**，在 3:4 下是 **1080×1440**。
`resolutionPresetsFor(aspect)` 现算，长边补齐到 4 的倍数（H.264 编码器对奇数尺寸很不友好）。
16:9 仍返回原来那张 `RESOLUTION_PRESETS`，**历史尺寸一个都没动** ——
改了会让老设置导出的成品悄悄变形。

### 顺带修的三处

1. **码率按像素量分档**（`BITRATE_BY_PIXELS`）。原来按高度查表，在「画布恒为 16:9」时成立；
   9:16 的 1080×1920 高度比 1440p 横屏还高，像素量却只有 1/3，按高度查会白白胖一倍。
2. **`readStageGeometry` 加回抽屉 padding 前先判断**。
   竖版舞台宽度是比例算出来的，与抽屉无关；再加回 360px 就会用错宽度算换行。
   判据用 computed `aspect-ratio` 是否为 `auto`（确定信号），不靠视口宽度去猜。
3. **画布尺寸只留一个出处**（`ensureCanvasSize`）。
   原来「渲染当前帧 / 渲染全部 / 导出」三处各自比对尺寸，
   加比例后最容易出的错是「画布竖版、几何横版」，而且报错信息毫无指向。

### 验证

```
core 测试      541 项全过（新增比例/竖版渲染 14 项）
SFC 编译       12 个组件全过
node --check   4 个改动模块语法通过
```

新增的核心断言：

- 三种比例在**同样画布高度**下字号完全一致 —— 守住「缩放系数只看高度」，
  一旦有人把 `k` 改成 `min(W/refW, H/refH)` 之类立刻报错；
- 比例一致时左对齐锚点 `x ≈ 0`（版心正好铺满，没有横向补边）；
- 竖版三种对齐方式下锚点都在画布内（不被裁掉）；
- 竖版画布背景整幅铺满（`fillRect` 的宽高等于画布尺寸）。
