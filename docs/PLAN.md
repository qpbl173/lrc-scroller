### 经验教训（N9，值得牢记的一条）

> **`addEventListener` 与 `removeEventListener` 必须作用在同一个 EventTarget 上，  
> 且必须传入同一个函数引用 —— 否则永远清不掉。**
>
> 这个 bug 在本项目里出现了**两次**（进度条/音量、色相环），  
> 两次都是"加与删的目标或时机不一致"：
>
> | 位置               | 病症                                                                    |
> | ---------------- | --------------------------------------------------------------------- |
> | PlayerBar 进度条/音量 | 加在 `window`、从元素删 → 监听器永久残留 → 松手后进度条跟着鼠标走                              |
> | ColorPicker 色相环  | 加在元素、`setPointerCapture` 失败时元素收不到 `pointerup` → 监听器留在元素上 → 不按键划过就会改颜色 |
>
> 因此**收敛为唯一的实现** `composables/pointerDrag.js`：  
> 监听目标统一为 `window`、用登记表记录 `[type, handler]` 并在收尾时按表解绑、  
> 收尾幂等（`pointerup` 与 `pointercancel` 可能都到达）、坐标非法返回 `null` 而非 `0`。  
> 验收脚本还包了 `window.addEventListener/removeEventListener` 做**计数探针**，  
> 直接把"有没有泄漏"变成可测量的数字（add/remove 必须完全配对）。

> 说明（N1 的架构影响，值得记一笔）：  
> 模拟时钟不是"另写一套播放循环"，而是**与真实音频共用同一个 rAF 时钟驱动**。  
> 区别仅在于"当前时间从哪读"：
>
> - 有音频 → 读 `audio.currentTime`
> - 无音频 → 读 `performance.now()` 推算  
>   因此 `useAudioEngine` 暴露统一的 `currentTime` / `duration` / `play()` / `pause()` / `seek()`，  
>   上层（阶段 3 的滚动）完全不需要知道自己处在哪种模式。这是 N1 被安排进阶段 2 的原因 ——  
>   若拖到阶段 3 再补，滚动逻辑将被迫写两套分支。

## 0. 一句话产品定义

一个**双击打开就能用**的本地网页应用：导入音频 + LRC 歌词 → 自动滚动、高亮当前行 → 可深度调样式 → 可全屏展示 / 录制成视频导出。全程文件不出浏览器。

## 1. 技术选型（含"为什么不选另一个"）

| 关注点  | 选型                                                          | 理由                                                                   | 被否掉的方案                                                             |
| ---- | ----------------------------------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 框架   | **Vue 3 (`<script setup>`)**                                | 响应式天然适配"设置面板改一个值 → 全局样式立刻变"；模板语法对非科班维护者友好                            | React（心智负担更重）、Svelte（生态/资料少）                                       |
| 构建   | **Vite 5+**                                                 | 秒级冷启动、`base: './'` 可打包成纯静态目录直接用                                      | Webpack（配置重）                                                       |
| 语言   | **JavaScript（ESM）**                                         | 你的硬约束；用 **JSDoc + `// @ts-check`** 在编辑器里获得类型提示，既不引入 TS 编译又不裸奔        | TypeScript                                                         |
| 状态管理 | **Pinia**                                                   | 设置项 + 歌词 + 播放器状态需要跨组件共享，Pinia 比 `provide/inject` 更易调试（DevTools 可看快照） | 纯 `reactive` 全局单例（后期难维护）                                           |
| 样式   | **原生 CSS + CSS 变量**                                         | 所有可视化设置（颜色/字号/间距）直接映射成 `--lrc-*` 变量，一处改动全站生效，**零运行时开销**              | Tailwind（要装依赖+类名噪音）、CSS-in-JS（运行时开销、和"实时预览"叠加会掉帧）                  |
| 滚动实现 | **`<div>` 容器 + `translate3d` 位移 + `requestAnimationFrame`** | 见 §4.1 关键决策；GPU 合成层，长歌词不卡                                            | `scrollTop` 赋值（主线程布局）、`scrollIntoView`（无法控速度、会和用户手动滚动打架）           |
| 音频   | **原生 `<audio>` + Web Audio API（可选）**                        | `<audio>` 稳定、支持大文件流式；Web Audio 用于未来做波形/精确时钟                          | Howler.js（第三方依赖，原生已够）                                              |
| 时间同步 | **`requestAnimationFrame` 轮询 `audio.currentTime`**          | 你的硬约束；比 `timeupdate`（约 4 次/秒）平滑得多                                    | 只用 `timeupdate`（滚动一顿一顿）                                            |
| 视频导出 | **Canvas 2D + `MediaRecorder`（WebM/VP9 优先，MP4 兜底探测）**       | 你的硬约束；无需 WebCodecs 兼容性风险。**明确不支持透明通道导出**（见 §8 诚实边界）                  | `MediaRecorder` 透明 WebM（浏览器会丢弃 alpha）、ffmpeg.wasm（体积 30MB+，纯前端体验差） |
| 持久化  | **localStorage**                                            | 你的硬约束；加版本号 + 容错解析                                                    | IndexedDB（对"几百字节设置"是过度设计）                                          |
| 部署   | **静态文件**，`vite build` 后可直接双击 `index.html` 或丢到任意静态托管         |                                                                      |                                                                    |

**唯一需要装的东西**：`vue`、`vite`、`@vitejs/plugin-vue`、`pinia`。没有 UI 组件库、没有 CSS 框架、没有工具库（LRC 解析器自己写，约 150 行）。

```
   │  └─ animations.css        # 过渡曲线、reduced-motion 降级
   │
   └─ assets/samples/
      └─ demo.lrc              # 内置示例歌词，无文件也能试用
```

**分层铁律**：

- `core/` 里的文件**不允许** `import vue`。可以在浏览器跑，也可以在 Node 里跑 —— 这是"解析器能被自动化测试"的前提。
- `stores/` 只放数据和纯逻辑，不碰 DOM。
- `composables/` 是唯一允许操作 DOM / 音频 / raf 的地方。
- `components/` 只负责呈现和事件上抛。

## 3. 数据结构（核心契约）

### 3.1 歌词对象 `LyricsDoc`

```js
{
  version: 1,
  meta: {
    title:  '',        // [ti:]
    artist: '',        // [ar:]
    album:  '',        // [al:]
    by:     '',        // [by:]
    length: null,      // [length:] → 秒
    offsetMs: 0,       // [offset:] 正=整体提前，负=整体延后（沿用社区约定）
    raw: {}            // 未识别的标签原样保留，导出时不丢信息
  },
  lines: [ LyricLine, ... ],   // 已按 t 升序排好，且 t 唯一
  warnings: [ Warning, ... ],  // 非致命问题，UI 用黄色角标提示
  droppedLines: [ { index, text, reason } ] // 无时间标签被丢弃的行
}
```

### 3.2 歌词行 `LyricLine`

```js
{
  id:      'L12',          // 稳定唯一 id：滚动复用、打轴重排、撤销都靠它
  t:       12.34,          // 最终生效时间（秒）= 原标签时间 + meta.offsetMs/1000
  rawT:    12.14,          // 原始标签时间（保留，便于"用户改 offset 后重新计算"）
  text:    '歌词内容',      // 已去除时间标签的正文（trim 后）
  chars:   null,           // 逐字时间 LyricChar[]，仅增强 LRC 有；普通 LRC 恒为 null
  empty:   false,          // 空行（间奏占位）：常用于"这段没歌词"
  beat:    null,           // 【阶段5】吸附到的节拍序号
  locked:  false,          // 手动微调过，自动吸附不覆盖
  tags:    []              // 该行携带的其他标签原文（扩展用）
}
```

#### 3.2.1 逐字时间 `LyricChar`（仅增强 LRC）

```js
// 源文本：[00:01.00]<00:01.00>你好,<00:01.50>世界
// 解析为 ↓
chars = [
  { c: '你好,', t: 1.0 },   // c = 一个字（含跟随其后的标点）；t = 秒（浮点）
  { c: '世界',  t: 1.5 },
]
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `c` | `string` | 一个字。**标点跟随前一个字**，在解析阶段归组，渲染层不猜 |
| `t` | `number` | 该字开始唱的时间，**秒**（与 `LyricLine.t` 同单位，非毫秒） |

**必须遵守的四条约束**

1. **单位是秒**，不是毫秒。与 `tappingStore` 存的 `{t: 秒}`、`player.currentTime` 一致，全项目不做单位换算。
2. **`chars` 无数据时为 `null`，不是 `[]`**。普通 LRC 打轴出来的行没有逐字时间是常态而非异常，判空统一写 `chars == null`。
3. **标点跟随前一个字**。「你好，」只产生一个 `c`，`t` 取「好」的时间。把标点单独拆成一项会让卡拉 OK 高亮先亮字再亮标点，看起来像闪烁。
4. **一个标签后面跟多个字时不拆分**。`<00:01.00>你好` 直接作为 `{ c: '你好' }`。强行按字符均分时间会得到「看着精确、实际错位」的结果 —— 宁可粒度粗，不可编数据。

**降级必须可见**：任何丢弃/降级（无法解析的标签、逐字覆盖不住正文）都会在 `doc.warnings` 里留下 `LRC_ENHANCED_DROPPED` / `LRC_ENHANCED_MISMATCH`。**不存在静默丢失** —— 正文永远保留，丢的只是粒度。

#### 3.2.2 增强 LRC 的写入格式（双写）

导出同时产出两份，**内容逐行一致**，只是增强版多了 `<mm:ss.xx>`：

```
标准 LRC（主输出，任何播放器可播）
[00:01.00]你好,世界

增强 LRC（保留逐字，重新导入本应用不丢数据）
[00:01.00]<00:01.00>你好,<00:01.50>世界
```

**标准标签 `[…]` 必须写在最前**。`<…>` 是附加信息，老播放器不认；先写 `[…]` 才能保证「主输出永远可播」。没有 `chars` 的行在增强文件里原样写正文，**不伪造逐字时间**。

## 4. 三个关键技术决策（决定成败）

### 4.1 滚动：位移而不是 `scrollTop`

- 舞台是一个 `overflow: hidden` 的容器，内部一个 `.lines` 轨道。
- rAF 每帧算 `y = 当前行offsetTop + 行高/2 → 使其落在容器中心`，然后 `track.style.transform = translate3d(0, -y px, 0)`。
- **当前行放大用 `transform: scale()`**，不占布局空间 → 不会引起重排 → 不会滚动抖动（你的硬约束）。
- 每帧只写一个 `transform`，不读布局（`offsetTop` 只在歌词/设置变化时缓存一次到数组里），彻底避免 **布局抖动（layout thrashing）**。
- 播放时用 **指数平滑**（`y += (targetY - y) * k`，k 按帧间隔归一化）或按 `transitionMs` 直接设 `transition` 让 CSS 补间；暂停时立即对齐。

### 4.2 用户手动滚动 vs 自动跟随（这是最容易做砸的地方）

状态机：

```
FOLLOWING ──(检测到用户 wheel / touchmove / 拖动滚动条)──▶ USER_SCROLLING
USER_SCROLLING ──(3 秒无操作 且 未按"锁定"按钮)──▶ FOLLOWING
USER_SCROLLING ──(点击"回到当前行" / 按 Home 键)──▶ FOLLOWING(立即对齐)
```

- 检测方式：监听 `wheel`、`touchstart`、`keydown(PgUp/PgDn/↑/↓)`；**不监听 `scroll` 事件**（因为我们自己用 transform，不产生 scroll）。
- **播放继续走，但视图不强拉回** —— 你的硬约束。用户回到底部时自动恢复。
- UI 上给一个小胶囊按钮："已暂停跟随 · 回到当前行"。

### 4.3 歌词性能（长歌词，2000 行以上）

三层防护：

1. **只渲染可视窗口 ± 40 行**（虚拟滚动）。用固定行高假设做二分定位，行高随字号/行距变化时重算缓存。
2. **行高必须可预测**：普通行统一高度；只有当前行用 `transform` 放大（不改高度）→ 这让虚拟化计算变成 O(log n) 二分，而不是测量 DOM。
3. **文本节点缓存**：行内容做成 `v-memo` 或 `key=id` 的稳定列表，切行只改两个 class，不重建 vnode。

## 5. LRC 解析规则（明确边界，防止"猜"出来的 bug）

**支持**

- 基础标签：`[mm:ss.xx]`、`[mm:ss.xxx]`、`[mm:ss]`、`[mm:ss:xx]`（冒号当小数点，兼容旧格式）
- 时间可为 `[00:12.34]` 也可为 `[1:02.5]`（一位分钟）
- **一行多标签**：`[00:12.00][01:20.00]歌词` → 展开成两行，`id` 不同
- **元数据**：`[ti:] [ar:] [al:] [by:] [offset:] [length:] [re:] [ve:]`，未知标签进 `meta.raw`
- **offset**：`[offset:+500]` = 整体提前 0.5s（社区约定：最终时间 = 原时间 − offset/1000）。UI 里用大白话写"整体偏移（正数=歌词提前）"，并在改 offset 时**基于 `rawT` 重算**，不会累积误差。
- **乱序**：解析完统一按 `t` 升序排序（稳定排序，同时间保持原文件顺序）
- **重复时间**：保留两行（不静默丢弃），标 `warnings: DUPLICATE_TIME`，UI 提示"第 X 行与第 Y 行时间重复"
- **增强格式（已支持）**：`<00:12.34>` 行内逐字时间戳 → 解析进 `LyricLine.chars`（见 3.2.1，标点跟随前一个字）。解析失败/降级**必须留下警告**，绝不静默丢失
- 编码：`FileReader` 读为 `ArrayBuffer` → **先试 UTF-8，出现 U+FFFD 则回落 GBK**（`TextDecoder('gbk')`），中文歌词最常见的坑
- 行尾 `\r\n`、BOM（`\uFEFF`）都要吃掉

**边界行为（必须有明确表现）**

| 场景                 | 行为                                              |
| ------------------ | ----------------------------------------------- |
| 空文件 / 全空白          | 不崩，`lines: []`，舞台显示"未导入歌词"，示例歌词按钮               |
| 无任何时间标签            | 全部进 `droppedLines`，提示"没有找到时间标签，已按纯文本加载，可进入打轴模式" |
| 时间标签但无正文           | 生成 `empty: true` 行（间奏），**建议不要删**，删了会让滚动跳变       |
| 时间为负               | 归零并警告                                           |
| offset 导致负时间       | 归零并警告                                           |
| 超大文件（>2MB / >1 万行） | 解析放 `Web Worker`，UI 显示进度，不阻塞白屏                  |

10. 设置面板含「虚化」分组与三个参数控件 + 模式下拉。

> **虚化的精确语义**（实现时明确下来的，避免歧义）：  
> 过渡区是跨度 `fadeRows` 的斜坡，`over = fadeRows` 处**恰好降到 0**。  
> 即 `fadeRows=5` 时第 1~4 行部分可见、第 5 行正好不可见；  
> 想"5 行都看得见"就把过渡行数设为 6。  
> 另外：**虚化开启时不再叠加 past/upcoming 明暗基准** ——  
> 需求原文要求实体区"完全不透明"（=1），叠加基准会让它实际显示为 0.38，与要求冲突。  
> 虚化关闭时才回落到阶段 3 的按行明暗区分。

8. 刷新页面 → 所有设置原样恢复。
9. 点"重置" → 回到默认值，且 localStorage 被清空（DevTools → Application 检查）。
10. 开系统"减少动态效果" (prefers-reduced-motion) → 过渡自动关闭，功能不受影响。
11. 长歌词（注入 2000 行合成 LRC）→ 播放 30s 帧率 ≥ 55fps（Performance 面板 FPS 计数）。
12. 移动端 375px 宽 → 布局不溢出、设置抽屉可滚、按钮可点（触摸目标 ≥ 44px）。

> **实测修正（阶段 3 结论，与方案初稿不同，特此记录）**
>
> 初稿计划对长歌词做"只渲染可视窗口 ±40 行"的虚拟滚动，  
> 理由是担心 2000 行会产生约 15 万像素的轨道高度、超出 GPU 纹理上限而掉帧。
>
> **实测否定了这个判断**：2000 行（轨道实测 157,294px）播放 30 秒为  
> **60fps、0 长任务、0 慢帧、堆 25MB**；加到 10000 行（轨道约 136 万像素）仍是  
> **60fps、最差帧 16.8ms、堆 65MB**。现代浏览器对超长合成层的处理比预期好得多。
>
> 因此**决定不实现虚拟滚动**，改为全量渲染 + `transform` 单层合成。  
> 少一层复杂度就少一类隐患（窗口计算错位导致的空白/跳行）。  
> 相关工具函数（`computeVisibleRange` 等）已写好并测过，但最终判定为不必要而移除；  
> 若未来在低端机上真的遇到掉帧，可按记录重新引入。

- 全屏**不能**是进入展示模式的前提：iOS Safari 不支持任意元素全屏，因此全屏失败只降级为 `fixed + 100dvh` 的伪全屏，功能不受影响。

## 8. 诚实的技术边界（先讲清楚，避免后面失望）

1. **透明通道视频导出基本不可行**。`MediaRecorder` 的 VP8/VP9 WebM 在 Chrome 里会把 alpha 通道丢弃；真正可行的路径是 WebCodecs + 自己封装 WebM（工作量大、兼容性差）。所以我把"透明"标为**实验功能**，并在 UI 里不承诺成功。**绿幕/黑幕是可靠方案**。
2. **导出不是"渲染加速"，是实时录制**。录 3 分钟的歌词就要等 3 分钟，且必须保持页面在前台。这是纯前端无后端的必然代价。
3. **不支持 MP3/AAC 等有损音频解码成 WAV 导出**（不做音频重编码），导出视频直接复用原始音频轨。
4. **localStorage 只存设置，不存音频**。刷新后需要重新选音频文件（浏览器安全模型限制，纯前端无法静默保存大文件）。
5. **iOS Safari 的全屏与自动播放限制最多**，会有降级体验（伪全屏 + 需用户手势触发播放）。
6. **不做的功能**（除非你后续要求）：在线歌词搜索、音高/人声分离、多轨字幕、账号同步。
